# ربات تلگرام استوک لند — مستندات کامل پروژه

> **نسخه:** نهایی (بهینه‌سازی‌شده)  
> **استفاده:** این فایل را به Claude بدهید تا بدون نیاز به توضیح مجدد، پروژه را کامل بشناسد.

-----

## ۱. معرفی پروژه

ربات تلگرام فروشگاه موبایل **استوک لند** (`stland.ir`)

- زبان: **Python 3.13**
- کتابخانه اصلی: **python-telegram-bot 22.7**
- استقرار: **وی‌پی‌اس اختصاصی** (systemd) — بدون Railway
- معماری: Bot polling — یک پروسه‌ی تنها (`bot.py`)
- **هیچ پورتی روی سرور باز نمی‌کند** — فقط خروجی به تلگرام

-----

## ۲. ساختار فایل‌ها

```
├── bot.py          # ربات اصلی — تمام منطق ربات اینجاست
├── requirements.txt
│
├── data.json       # متن بخش‌های ربات (پشتیبانی، آدرس، ...)
├── banner.json     # بنرهای هر بخش (file_id + active)
├── workhours.json  # ساعت کاری
├── buttons.json    # دکمه‌های inline هر بخش
├── settings.json   # تنظیمات (notify_new_user, store_open)
├── stats.json      # آمار بازدید بخش‌ها
├── menu.json       # ترتیب و label دکمه‌های منوی اصلی
├── places.json     # لوکیشن روی نقشه برای هر بخش
├── backups.json    # فهرست بکاپ‌های خودکار (تا ری‌استارت را دوام بیاورد)
├── admins.json     # مدیرهای افزوده‌شده از پنل (مالک همیشه از .env می‌آید)
├── faq.json        # سؤال‌های آماده (کلیدواژه → پاسخ خودکار، با عکس اختیاری)
├── unmatched.json  # سؤال‌هایی که هیچ جوابی نداشتند
├── broadcast.json  # کار پخش در جریان/زمان‌بندی‌شده (برای ادامه پس از ری‌استارت)
└── users.db        # SQLite — کاربران
```

## ۳. متغیرهای محیطی

|متغیر          |اجباری |توضیح                                               |
|---------------|-------|----------------------------------------------------|
|`BOT_TOKEN`    |✅      |توکن ربات از BotFather                              |
|`ADMIN_ID`     |✅      |آیدی عددی مدیر — یک آیدی، یا چند آیدی با کاما        |

`ADMIN_ID` می‌تواند چند آیدی داشته باشد: `ADMIN_ID=11111111,22222222`.
**اولین آیدی «مالک» است** — تنها کسی که مدیر اضافه/کم می‌کند، بک‌آپ می‌گیرد و
بازمی‌گرداند، و گزارش خطا برایش می‌رود. مدیرهای بعدی به پنل و پیام‌های
مشتری‌ها دسترسی دارند. مدیرهای `.env` از داخل پنل حذف نمی‌شوند (تا کسی
نتواند خودش یا مالک را بیرون بیندازد)؛ مدیرهایی که از پنل اضافه شده‌اند در
`admins.json` می‌مانند و با بک‌آپ هم منتقل می‌شوند.

همین دو متغیر کافی است. ربات پورتی باز نمی‌کند، رمزی نمی‌خواهد و هیچ سرویسی روی اینترنت expose نمی‌کند — تمام مدیریت از پنل ادمین داخل خود تلگرام (`/admin`) انجام می‌شود.

## ۳.۱. استقرار روی وی‌پی‌اس (systemd)

این پروژه با گیت‌هاب و اجرای مستقیم روی وی‌پی‌اس (بدون Railway/Heroku) کار می‌کند و **کاملاً مستقل از سایر پروژه‌های همان سرور** است — فقط منابع سرور مشترک است، نه فایل‌ها، دیتابیس، یا پورت.

```bash
# ۱) کلون در مسیر اختصاصی خودِ همین پروژه
git clone <repo-url> /opt/telegram-bot
cd /opt/telegram-bot

# ۲) محیط پایتون مجزا
python3 -m venv venv
venv/bin/pip install -r requirements.txt

# ۳) فایل .env با BOT_TOKEN و ADMIN_ID
cp .env.example .env   # سپس مقداردهی کنید
```

نمونه سرویس systemd در `deploy/telegram-bot.service` آماده است — فقط مسیرها و `User` را مطابق سرور خودتان تنظیم کنید:

```bash
sudo cp deploy/telegram-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now telegram-bot
sudo journalctl -u telegram-bot -f
```

برای آپدیت بعدی:

```bash
cd /opt/telegram-bot && git pull && bash deploy/restart.sh
```

`deploy/restart.sh` ری‌استارت امن است: سرویس را متوقف می‌کند، اگر پروسه‌ای از
همین پروژه جا مانده باشد فقط همان را می‌بندد (به سرویس‌های دیگر سرور کاری
ندارد)، وضعیت `failed` را پاک می‌کند، دوباره استارت می‌زند و در پایان وضعیت و
۱۵ خط آخر لاگ را نشان می‌دهد.

اگر مشکلی بود:

```bash
bash deploy/doctor.sh
```

می‌خواهید بدانید روی این وی‌پی‌اسِ مشترک چه چیزهایی نصب است؟

```bash
sudo bash deploy/vps-report.sh              # روی صفحه
sudo bash deploy/vps-report.sh > /root/vps-report.txt   # ذخیره در فایل
```

گزارش شامل: سیستم‌عامل و منابع، **پورت‌های باز و پروسه‌ی پشت هرکدام**،
سرویس‌های systemd، وب‌سرور و سایت‌هایش، دیتابیس‌ها، زبان‌ها و ابزارها،
کانتینرهای داکر، پکیج‌های مهم و تاریخچه‌ی نصبشان، کران‌جاب‌ها، پروژه‌های
گیت روی سرور با حجمشان، فایروال، و وضعیت خودِ این ربات.

اسکریپت **فقط می‌خوانَد** — چیزی نصب، حذف یا ری‌استارت نمی‌کند، پس روی
پروژه‌های دیگرِ همان سرور هیچ اثری ندارد.

## ۴. پایگاه داده SQLite (`users.db`)

### جدول `users`

```sql
user_id INTEGER PRIMARY KEY
username TEXT
first_name TEXT
joined_at TEXT
last_seen TEXT
is_blocked INTEGER DEFAULT 0   -- ادمین کاربر را بلاک کرده
has_left   INTEGER DEFAULT 0   -- کاربر ربات را بلاک/حذف کرده (از پخش کنار می‌رود)
source     TEXT DEFAULT ''      -- منبع ورود از deep-link (فقط یک‌بار ثبت می‌شود)
open_msg_at TEXT DEFAULT ''     -- زمان اولین پیام بی‌جواب (با پاسخ مدیر خالی می‌شود)
reminded   INTEGER DEFAULT 0    -- یادآوری ۲ساعته فرستاده شده یا نه

INDEX: idx_ls ON (last_seen)
```

### جدول `threads`

نقشه‌ی «کدام پیام در چت کدام مدیر مربوط به کدام مشتری است» — پایه‌ی
پاسخ‌دادن با ریپلای.

```sql
admin_id INTEGER      -- چت مدیر
msg_id   INTEGER      -- پیام فوروارد‌شده یا کارت مشخصات، داخل همان چت
user_id  INTEGER      -- مشتری صاحب پیام
ts       TEXT         -- برای پاکسازی دوره‌ای (۶۰ روز)
PRIMARY KEY(admin_id,msg_id)
```

## ۷.۱. لینک‌های ورودی (deep link)

`t.me/<bot>?start=insta` منبع ورود کاربر را ثبت می‌کند — برای خودِ کاربر
کاملاً نامرئی، و در «📊 آمار» پنل به‌صورت «🎯 مشتری‌ها از کجا آمده‌اند»
نمایش داده می‌شود.

- فقط **اولین** منبع ثبت می‌شود؛ ورودهای بعدی آن را بازنویسی نمی‌کنند
- ورودی با `_SRC_RE` اعتبارسنجی می‌شود (فقط حروف/عدد/`_`/`-`، حداکثر ۳۲ کاراکتر)
- برچسب‌های خوانا در `SOURCE_LABELS` — هر مقدار ناشناخته خام نمایش داده می‌شود

نمونه لینک‌ها: `?start=insta` · `?start=bale` · `?start=site` · `?start=card` ·
`?start=qr`

## ۸.۰. زبان بصری ربات

همه‌ی پیام‌ها یک قالب واحد دارند (`build_msg`) و با `parse_mode="HTML"` ارسال
می‌شوند:

```
<b>عنوان بخش</b>
━━━━━━━━━━━━━━━
متن
[دکمه]  [دکمه]
```

- محتوای ادمین با `esc()` (همان `html.escape`) پاکسازی می‌شود تا کاراکترهایی
  مثل `<` پیام را نشکنند
- `_fit()` سقف تلگرام را رعایت می‌کند: ۱۰۲۴ برای caption عکس، ۴۰۹۶ برای متن
- `status_line()` وضعیت زنده می‌سازد: «🟢 هم‌اکنون باز هستیم · تا ۲۳:۰۰» یا
  «🔴 هم‌اکنون بسته است · بازگشایی ۱۱:۰۰»
- `/start` با نام کاربر سلام می‌کند و همین نوار وضعیت را نشان می‌دهد
- پیش از هر پاسخ، نشانگر «در حال نوشتن» فرستاده می‌شود (`typing()`)
- `disable_web_page_preview=True` تا پیش‌نمایش لینک، پیام را شلوغ نکند

## ۸.۱. لینک‌های بخش → دکمه

لینک‌های داخل متن هر بخش **خودکار** به دکمه‌ی inline تبدیل می‌شوند و عنوان
فارسی می‌گیرند (`section_links`) — ادمین لازم نیست کاری بکند، فقط لینک را در
متن بنویسد. دکمه‌ی «✨ ساخت دکمه از لینک‌های متن» هم برای تبدیل دائمی هست — اینستاگرام،
تلگرام، بله، ایتا، روبیکا، واتساپ، آپارات، یوتیوب و… ؛ دامنه‌ی خود فروشگاه
(`SHOP_SITE`) «🌐 وب‌سایت فروشگاه» می‌شود.

همان لینک‌ها **از متن پنهان می‌شوند** (`strip_button_links`) چون دکمه جایشان را
گرفته — همراه با برچسب بالای‌شان («📸 Instagram») که دیگر مرجعی ندارد، چون نام
روی خود دکمه نوشته شده. مثل لینک نقشه، این کار **غیرمخرب** است: متن اصلی در
`data.json` می‌ماند و با غیرفعال‌کردن دکمه‌های بخش برمی‌گردد.

## ۸.۲. پیام آزاد کاربران و پاسخ مدیر

هر چیزی که کاربر بفرستد و دکمه‌ی منو نباشد — **متن، عکس، ویس، ویدیو، فایل،
مخاطب یا استیکر** — برای **همه‌ی مدیرها فوروارد** می‌شود و به کاربر تأیید
داده می‌شود. نوع پیام در اعلان مشخص است (🎤 ویس، 🖼 عکس، …).

### پاسخ = ریپلای در چت خود تلگرام

**هیچ پنل یا حالت جداگانه‌ای برای پاسخ وجود ندارد و نباید ساخته شود.** مدیر
در چت خودش با ربات، روی پیام فوروارد‌شده (یا کارت مشخصات زیرش) **ریپلای**
می‌زند و همان پیام عیناً به مشتری می‌رسد:

- `reply_relay` در **گروه ۱-** ثبت شده تا زودتر از هر هندلر دیگری اجرا شود
- اگر `reply_to_message` در جدول `threads` باشد → `copy_message` به مشتری
  (بدون برچسب «فوروارد از» — انگار خودِ فروشگاه نوشته) و سپس
  `ApplicationHandlerStop` تا پیام دوباره پردازش نشود
- اگر ریپلای بی‌ربط باشد، هندلر کاری نمی‌کند و پیام مسیر عادی خودش را می‌رود
- پاسخ خودِ مدیر هم در `threads` ثبت می‌شود تا رشته‌ی گفتگو ادامه پیدا کند
- موفقیت با ری‌اکشن 👍 روی پیام مدیر اعلام می‌شود (بدون شلوغ‌کردن چت)؛
  اگر مشتری ربات را بلاک کرده باشد، پیام خطا می‌آید و `has_left` ثبت می‌شود
- هر نوع پیامی کار می‌کند: متن، عکس، ویس، ویدیو، فایل، استیکر

### تأیید آگاه از ساعت کاری

پیامِ «دریافت شد» به مشتری بسته به `is_open()` فرق می‌کند: در ساعت کاری
«به‌زودی پاسخ می‌دهند»، و بیرون از آن «الان بسته‌ایم — پاسخ شما فردا از
ساعت ۱۱:۰۰ می‌آید» (`next_open_text` نزدیک‌ترین شیفتِ نیامده را در ۷ روز
آینده پیدا می‌کند).

### پیام‌های بی‌جواب

- با هر پیام مشتری `open_msg_at` **فقط اگر خالی باشد** پر می‌شود — پس پیام
  دوم و سوم سنِ انتظار را صفر نمی‌کند
- پیامی که همان لحظه **پاسخ خودکار** گرفته در این صف نمی‌نشیند، وگرنه
  سؤال‌های جواب‌داده‌شده صف را باد می‌کردند و دو ساعت بعد یادآوری بی‌مورد
  می‌فرستادند
- اولین ریپلای مدیر آن را خالی می‌کند (`mark_answered`)
- شمارش در صفحه‌ی اصلی پنل + صفحه‌ی `pending` با فهرست و سنِ هرکدام
- «🔔 نشانم بده در چت» هر پیام بی‌جواب را به‌صورت **ریپلای** بالا می‌آورد،
  پس یک تپ و مدیر دقیقاً روی همان پیام مشتری است
- `_pending_loop` پیام‌های بیش از ۲ ساعت را **یک‌بار** یادآوری می‌کند
  (ستون `reminded`)

## ۸.۳. سؤال‌های آماده (پاسخ خودکار)

**هیچ دکمه‌ای به منوی مشتری اضافه نمی‌کند.** مشتری سؤالش را مثل همیشه
می‌نویسد؛ اگر کلیدواژه‌ای از `faq.json` در متنش باشد، همان لحظه پاسخ
می‌گیرد **و پیامش باز هم برای مدیرها فوروارد می‌شود** (با برچسب «✅ پاسخ
خودکار داده شد») تا اگر ناقص بود کاملش کنند.

```json
{"id":"b1a2c3d4","keys":["گارانتی","ضمانت"],"answer":"…",
 "enabled":true,"hits":12,
 "photo":"AgACAgQ…","photo_at":"2026-08-22 09:12:00"}
```

- **تطبیق فقط با کلیدواژه‌های ادمین** — هیچ حدسی در کار نیست. اگر چیزی
  جور نشد، ربات ساکت می‌ماند و فقط فوروارد می‌کند؛ جواب غلط از جواب ندادن
  بدتر است.
- `faq_norm`: ي/ك عربی → فارسی، ارقام فارسی → انگلیسی، حذف نیم‌فاصله و
  علائم — تا نوشتار مشتری مانع تطبیق نشود
- **بلندترین کلیدواژه برنده است**، پس «گارانتی طلایی» بر «گارانتی» می‌چربد
- کلیدواژه‌ی کوتاه‌تر از ۲ حرف پذیرفته نمی‌شود
- لینک داخل پاسخ خودکار دکمه می‌شود و از متن پاک (مثل بقیه‌ی بخش‌ها)
- `hits` نشان می‌دهد هر سؤال چند بار به کار آمده
- در اولین اجرا چهار نمونه ساخته می‌شود که **همه خاموش‌اند** — تا ادمین
  متن را با کلمات خودش ننوشته، چیزی به مشتری نمی‌رود
- کلید خاموشی: `settings.faq_auto`

### عکس روی پاسخ (لیست قیمت روزانه)

هر سؤال آماده می‌تواند یک عکس داشته باشد. کاربردش «قیمت» است: عکسِ لیست
قیمتِ امروز، با **مهر تاریخ** روی خودِ جواب («🗓 ۳۱ مرداد») تا اگر روزی
آپدیت نشد، مشتری خودش بفهمد و بپرسد.

- برخلاف بنرها، **بزرگ‌ترین نسخه** ذخیره می‌شود — خوانا بودن متنِ داخل
  عکس از چند کیلوبایت صرفه‌جویی مهم‌تر است
- `file_id` یعنی فقط یک‌بار آپلود، بی‌نهایت ارسال
- **میان‌بر روزانه:** عکس را با کپشن `#قیمت` بفرستید — بدون رفتن به پنل،
  عکسِ همان سؤال آماده عوض می‌شود و اگر خاموش بود روشن می‌گردد
- حالت‌های صریح (بنر، پخش همگانی) همیشه بر این میان‌بر مقدم‌اند

### میان‌بر `#کلیدواژه` هنگام پاسخ

مدیر موقع ریپلای به مشتری، به‌جای تایپ دوباره فقط `#گارانتی` می‌نویسد و
همان پاسخ آماده (با عکسش) برای مشتری می‌رود. با چند مدیر یعنی جواب‌ها
یکدست هم می‌مانند.

- فقط برای پیام **متنی** و وقتی کل پیام یک کلمه‌ی `#…` باشد؛
  `#گارانتی دارد` یا عکسی با کپشن `#گارانتی` عیناً کپی می‌شود
- کلیدواژه‌ی ناموجود → به مدیر خبر می‌دهد و **چیزی برای مشتری نمی‌فرستد**
- جمله‌ی «همکاران ما هم دیدند» در این حالت نمی‌آید — یک آدم واقعی فرستاده
- کلید خاموشی: `settings.faq_shortcut`

## ۸.۴. سؤال‌های بی‌پاسخ (`unmatched.json`)

پرسش‌هایی که هیچ سؤال آماده‌ای جوابشان را نداشت، ثبت می‌شوند تا فهرست
سؤال‌های آماده به‌جای حدسِ ادمین، از خودِ مشتری‌ها ساخته شود.

- تجمیع بر اساس متنِ نرمال‌شده با شمارنده (`count`) — پرتکرارها اول،
  در تساوی تازه‌ترها بالاتر
- هر رکورد `id` ثابت دارد و دکمه با همان id ساخته می‌شود، نه شماره‌ی ردیف:
  اگر بین نمایش صفحه و تپِ ادمین سؤال تازه‌ای برسد ترتیب عوض می‌شود و
  ردیفِ اشتباه باز می‌شد
- **فقط پیام مشتری‌ها**: متن آزادِ خودِ مدیر نه پاسخ خودکار می‌گیرد و نه
  اینجا ثبت می‌شود
- فقط پیام‌های ۳ تا ۲۰۰ نویسه‌ای؛ سقف ۲۰۰ رکورد
- در پنل: محتوای ربات ← سؤال‌های آماده ← «❓ سؤال‌های بی‌پاسخ»
- تپ روی هر سؤال، ساختِ سؤال آماده را با همان متن جلوی چشم شروع می‌کند
- کلید خاموشی: `settings.log_unmatched`

> نکته: PTB در هر گروه فقط اولین هندلرِ منطبق را اجرا می‌کند. چون
> `photo_handler` و `document_handler` زودتر ثبت می‌شوند، برای غیرادمین باید
> صریحاً به `user_media_handler` واگذار کنند — وگرنه پیام مشتری بی‌صدا دور
> ریخته می‌شود.
با گزینه‌ی «دریافت پیام کاربران» در تنظیمات قابل خاموش‌کردن است؛ در آن حالت
فقط راهنمای منو نمایش داده می‌شود.

## ۸.۲. ساعت کاری — شیفت‌های نیمه‌شب‌گذر

شیفت می‌تواند از نیمه‌شب رد شود (مثلاً `22:00-02:00`). `in_shift()` این حالت
را با مقایسه‌ی `from > to` تشخیص می‌دهد و `is_open()` شیفتِ نیمه‌شب‌گذرِ **روز
قبل** را هم بررسی می‌کند.

ورودی شیفت اعتبارسنجی می‌شود (`HH:MM` دقیق، ارقام فارسی هم پذیرفته می‌شود)؛
ورودی نامعتبر ذخیره نمی‌شود و ادمین در همان حالت می‌ماند تا دوباره وارد کند.

## ۹. سیستم Anti-Spam (دو فازی)

```python
_rate:       dict  # uid → [timestamps]
_warned:     dict  # uid → زمان اولین هشدار
_hard_block: dict  # uid → blocked_until
_RATE_MAX = 8      # حداکثر کلیک در پنجره
_RATE_WIN = 10.0   # پنجره ۱۰ ثانیه
_HARD_BLOCK = 10.0 # ۱۰ ثانیه بلاک سخت
```

**جریان:**

1. کلیک ۱-۸ در ۱۰ ثانیه → مجاز
1. کلیک ۹ام → **warn** → popup «آرامتر کلیک کنید» — ریپلای نمی‌آید
1. کلیک بعد از warn → **block** → ۱۰ ثانیه بی‌صدا

**استثناها:**

- `ADMIN_ID`: از همه چک‌ها معاف
- `req_phone` mode: از spam_check معاف (حین ثبت شماره تماس نباید بلاک شود)

**Cleanup:** هر ۶ ساعت توسط `_spam_cleanup_loop` — `_rate`, `_warned`, `_hard_block`, `_block_cache`, `_seen_uids` پاک می‌شوند.

## ۱۰. Background Tasks (asyncio.ensure_future در post_init)

|تابع                    |فرکانس             |کار                             |
|------------------------|-------------------|--------------------------------|
|`_spam_cleanup_loop()`  |هر ۶ ساعت          |پاک کردن dicts anti-spam        |
|`_stats_flush_loop()`   |هر ۳۰ ثانیه        |ذخیره stats اگر dirty           |
|`_auto_backup_loop(bot)`|هر ۳۰ دقیقه چک    |بکاپ هفتگی به مالک — جمعه ۳ بامداد|
|`_bc_loop(bot)`         |هر ۲۰ ثانیه        |ادامه‌ی پخش نیمه‌تمام و اجرای پخش زمان‌بندی‌شده|
|`_pending_loop(bot)`    |هر ۳۰ دقیقه        |یادآوری پیام‌های بیش از ۲ ساعت بی‌جواب|

همه با `_spawn(...)` ساخته می‌شوند: بدنه‌ی هر حلقه `try/except` دارد تا یک
خطا حلقه را تا آخر عمر پروسه نکشد، و اگر تسکی به هر دلیل بمیرد در لاگ
گزارش می‌شود — با `ensure_future` خالی، مرگِ تسک بی‌صدا بود و یک قابلیت
تا ری‌استارت بعدی از کار می‌افتاد بدون اینکه کسی بفهمد.

**مدیریت خطا:** `on_error` تمام خطاهای گرفته‌نشده را می‌گیرد — به کاربر پیام
می‌دهد و traceback را برای ادمین می‌فرستد (حداکثر یک گزارش در دقیقه).

## ۱۱. سیستم Backup

> ⚠️ **نکته حیاتی برای توسعه:** `users.db` در حالت WAL باز است. جایگزینی فایل
> زیر پای اتصالِ باز باعث می‌شود `users.db-wal` قدیمی روی داده‌ی تازه اعمال شود
> و بازگردانی **بی‌صدا بی‌اثر بماند**. `restore_backup` به همین دلیل اتصال را
> می‌بندد، فایل را می‌نویسد، `-wal`/`-shm` را پاک می‌کند و دوباره `init_db()`
> می‌زند. این ترتیب را به‌هم نزنید.

**بکاپ دستی:** دکمه «💾 دریافت پشتیبان» در پنل ادمین — هر وقت خواستید  
**بکاپ خودکار:** هفته‌ای یک‌بار، **جمعه ساعت ۳ بامداد** به وقت تهران
(`BACKUP_WEEKDAY=6`، `BACKUP_HOUR=3`)

تاریخ آخرین بکاپ در `settings.last_auto_backup` می‌ماند، پس **ری‌استارت
باعث بکاپ تکراری نمی‌شود** — قبلاً این تاریخ فقط در حافظه بود و هر
ری‌استارتِ بعد از ساعت هدف یک بکاپ اضافه می‌فرستاد.

اگر ربات روز جمعه خاموش باشد، `BACKUP_MAX_GAP=7` تضمین می‌کند بیشتر از
یک هفته بدون بکاپ نمانیم: اولین فرصت بعدی، هر روزی که باشد، بکاپ می‌رود.

**محتوای بکاپ (ZIP):**
`data.json`, `banner.json`, `workhours.json`, `buttons.json`,
`settings.json`, `stats.json`, `menu.json`, `places.json`, `admins.json`,
`faq.json`, `unmatched.json`, `users.db`

**Rotation:** حداکثر ۵ بکاپ در چت مالک — ششمی که بیاید اولی حذف می‌شود.
با زمان‌بندی هفتگی یعنی حدود ۵ هفته سابقه.  
نگهداری `_backup_registry = [{"msg_id", "file_id", "date"}]`

**بازگردانی:**

- از فایل: دکمه «📥 بارگذاری فایل» → فایل ZIP ارسال
- یک‌کلیکه: دکمه‌های «♻️ تاریخ» برای هر بکاپ هفتگی — **با صفحه تأیید**

پیش از هر بازگردانی:

1. ZIP اعتبارسنجی می‌شود (امضای SQLite در `users.db`، معتبر بودن هر JSON،
   سقف حجم) — اگر خراب باشد، هیچ فایلی دست‌نخورده باقی می‌ماند
1. از وضعیت فعلی یک نسخه ایمنی در `pre_restore.zip` گرفته می‌شود

## ۱۲. سیستم Broadcast

پخش همگانی سه‌مرحله‌ای است: **مخاطب → پیام → ارسال یا زمان‌بندی.**

### مخاطب (`bc_uids`)

|کلید        |چه کسانی                                  |
|------------|-------------------------------------------|
|`all`       |همه‌ی کاربران                              |
|`active30`  |`last_seen` در ۳۰ روز اخیر                 |
|`new7`      |`joined_at` در ۷ روز اخیر                  |
|`cold90`    |بیش از ۹۰ روز غایب (کمپین بازگشت)          |
|`src:{منبع}`|کسانی که از یک لینک ورودی خاص آمده‌اند       |

بلاک‌شده‌ها (`is_blocked`)، کسانی که ربات را حذف کرده‌اند (`has_left`) و خودِ
مدیرها همیشه بیرون‌اند. منبع با `_SRC_RE` اعتبارسنجی و کوئری پارامتری اجرا
می‌شود.

### مقاوم در برابر ری‌استارت

کار پخش در `broadcast.json` نگهداری می‌شود:

```json
{"id":"a1b2c3d4","text":"…","photo":null,"audience":"all",
 "queue":[111,222,…],"i":37,"ok":36,"fail":1,"gone":1,
 "by":11111111,"run_at":null,"status":"running"}
```

- بعد از هر ۲۰ ارسال (و در `post_shutdown`) شاخص `i` روی دیسک ذخیره می‌شود
- `_bc_loop` هر ۲۰ ثانیه کارِ نیمه‌تمام را از **نفر بعدی** ادامه می‌دهد —
  نه از اول، پس هیچ‌کس پیام تکراری نمی‌گیرد
- خطای شبکه پخش را نمی‌کشد؛ کار باقی می‌ماند و خودکار ادامه پیدا می‌کند
- تنها جایی که کار پاک می‌شود: پایان موفق، لغو دستی، یا `bc_kill`

### زمان‌بندی

`run_at` (timestamp) یعنی `status="pending"`؛ `_bc_loop` سر وقت اجرایش می‌کند.
ساعت دلخواه با `HHMM_RE` اعتبارسنجی می‌شود و اگر از الان گذشته باشد به فردا
موکول می‌گردد (`bc_next_at`). ارقام فارسی هم پذیرفته می‌شود.

### سایر نکات

- پیش از هر پخش، پیش‌نمایش پیام و تعداد گیرندگان نمایش داده می‌شود
- نرخ: `0.05s` بین هر پیام (~۲۰ msg/s، زیر حد Telegram)
- `RetryAfter`: اگر Telegram flood گفت، صبر می‌کند و یک‌بار دوباره می‌فرستد
- `Forbidden` → `mark_left(uid)`؛ آن کاربر از پخش‌های بعدی حذف می‌شود
- Progress هر ۲۰ پیام روی همان پیام وضعیت آپدیت می‌شود
- هم‌زمان فقط یک پخش — مدیر دوم پیام «یک پخش دیگر در جریان است» می‌گیرد

## ۱۴. پنل مدیریت (داخل تلگرام)

تمام مدیریت با دستور `/admin` در خود تلگرام انجام می‌شود — پنل وبی وجود ندارد.

**صفحه اصلی زنده است**: وضعیت باز/بسته بودن فروشگاه، ساعت کاری امروز، تعداد

شمارنده می‌گذارد. هر صفحه دو راه خروج دارد: «🔙 بازگشت» به والدِ منطقی و

|بخش              |کارها                                                     |
|-----------------|----------------------------------------------------------|

|⚙️ تنظیمات        |باز/بستن فروشگاه، اعلان‌ها، پشتیبان‌گیری و بازیابی            |

### لوکیشن روی نقشه

هر بخش می‌تواند یک لوکیشن داشته باشد. وقتی کاربر آن بخش را باز کند، علاوه بر
متن و بنر، یک **کارت نقشه‌ی بومی تلگرام** (`sendVenue`) هم دریافت می‌کند — نقشه
داخل خود تلگرام باز می‌شود و با یک لمس مسیریابی شروع می‌شود، بدون نیاز به لینک
گوگل‌مپ.

تنظیم: پنل → ✏️ محتوای ربات → 📝 بخش‌ها → بخش موردنظر → 📍 لوکیشن →
«📤 ثبت لوکیشن» → موقعیت را از منوی 📎 تلگرام بفرستید.

- هیچ API یا geocoding خارجی لازم نیست — مختصات مستقیم از خود تلگرام می‌آید
- لوکیشنِ فورواردشده (Venue) هم پذیرفته می‌شود و عنوان/آدرسش خودکار برداشته می‌شود
- آدرس پیش‌فرض از اولین خط متن همان بخش پر می‌شود و با «✏️ عنوان و آدرس» قابل تغییر است
- اگر `sendVenue` خطا بدهد، به `sendLocation` سقوط می‌کند
**یک کارت واحد:** تا وقتی لوکیشن یک بخش فعال است، کاربر **فقط همان کارت نقشه**
را می‌بیند — نقشه + نام + آدرس + دکمه‌های inline همان بخش. متن و بنر آن بخش
ارسال نمی‌شوند.

> محدودیت Bot API: `sendVenue` نه `caption` می‌پذیرد نه `photo`، و
> `sendMediaGroup` هم لوکیشن را ترکیب نمی‌کند. پس یک پیام واحدِ شاملِ
> بنر + متن + نقشه ممکن نیست. اما `sendVenue` **`reply_markup` می‌پذیرد**، پس
> دکمه‌های بخش زیر همان کارت می‌نشینند.

- آدرسِ داخل کارت هنگام ثبت لوکیشن، خودکار از متن همان بخش پر می‌شود (بدون
  لینک نقشه) و با «✏️ عنوان و آدرس» قابل ویرایش است
- با غیرفعال‌کردن لوکیشن، متن و بنر دقیقاً مثل قبل برمی‌گردند — هیچ داده‌ای
  حذف نمی‌شود
- `strip_map_links` لینک‌های نقشه (Google Maps، نشان، بلد، Waze، OpenStreetMap)
  و خط‌های اشاره‌گر مثل «آدرس در گوگل مپ 👇» را برمی‌دارد

### عکس‌ها

تلگرام هر عکس را در چند اندازه نگه می‌دارد. هنگام آپلود بنر، به‌جای بزرگ‌ترین
نسخه، سبک‌ترین نسخه‌ی با کیفیت کافی (عرض ≤ `BANNER_MAX_W`) انتخاب و `file_id`
آن ذخیره می‌شود:

- **آپلود فقط یک‌بار** — از آن پس همان `file_id` بی‌نهایت بار بدون آپلود مجدد
  ارسال می‌شود
- **حجم کمتر برای کاربر** — به‌جای نسخه‌ی چند مگابایتی، نسخه‌ی چند صد کیلوبایتی
- **تشخیص تکراری** — آپلود دوباره‌ی همان عکس (`file_unique_id`) دوباره ذخیره
  نمی‌شود
- **تامنیل جدا** (`thumb_id`, عرض ≤ `THUMB_MAX_W`) برای پیش‌نمایش داخل پنل
- پخش همگانی هم نسخه‌ی سبک را می‌فرستد — تفاوتش در ارسال به هزاران کاربر زیاد است

**چرا پنل وب حذف شد:** پنل وب زیرمجموعه‌ی همین پنل بود (پخش همگانی، پشتیبان‌گیری
و مدیریت منو را هم نداشت) و در اصل برای نمایش محصولاتِ خوانده‌شده از وردپرس
ساخته شده بود که آن هم حذف شد. با حذفش ربات دیگر هیچ پورتی باز نمی‌کند، رمزی
نمی‌خواهد و روی وی‌پی‌اس مشترک با هیچ پروژه‌ای تداخل ندارد.

## ۱۴.۲. عملکرد و سرعت

|تنظیم                       |مقدار|چرا                                          |
|----------------------------|-----|---------------------------------------------|
|`concurrent_updates`        |۳۲   |پیش‌فرض PTB **۱** است — یعنی آپدیت‌ها یکی‌یکی پردازش می‌شوند و یک ارسال کند، همه‌ی کاربران را پشت خود نگه می‌دارد|
|`connection_pool_size`      |۶۴   |تا ارسال‌های هم‌زمان پشت هم قفل نشوند         |
|`get_updates_read_timeout`  |۳۵ث  |long-polling پایدار                          |

نکات دیگر:

- `save_user` یک `UPSERT` است، نه `INSERT`+`UPDATE` — نصف کردن نوشتن روی مسیر
  داغِ هر پیام (به‌همراه throttle پنج‌دقیقه‌ای `_seen_uids`)
- کیبورد منوی اصلی کش می‌شود و فقط با `save_menu()`/`load_menu()` باطل می‌گردد
- بنرها با `file_id` ارسال می‌شوند (بدون آپلود مجدد) و از نسخه‌ی سبک استفاده می‌کنند

## ۱۵. چیزهایی که پیاده نشده (scope خارج از پروژه)

- **چت دوطرفه کاربر↔ادمین**: توصیه می‌شود از آیدی تلگرام ادمین در بخش پشتیبانی استفاده شود
- **PostgreSQL**: در صورت رشد به ۵۰۰۰+ کاربر
- **پنل تحت وب**: عمداً حذف شد — همه‌چیز از پنل تلگرام

## ۱۶. راه‌اندازی مجدد (Redeploy)

۱. بکاپ بگیرید (پنل ادمین → تنظیمات → پشتیبان‌گیری)
۲. deploy کنید
۳. بکاپ را restore کنید («📥 بارگذاری فایل» یا «♻️» از بکاپ خودکار)

**فایل‌هایی که بعد از redeploy بازمی‌گردند:**  
`data.json`, `banner.json`, `workhours.json`, `buttons.json`,  
`settings.json`, `stats.json`, `menu.json`, `users.db`

## ۱۷. نکات مهم برای توسعه آینده

1. **اضافه کردن section جدید:** باید در `SECTION_NAMES`, `SECTION_ORDER`, `DEFAULT_MENU` و `DEFAULT_SEC_WH` اضافه شود
1. **Callback جدید برای کاربر:** باید در `_USER_CB_PREFIXES` اضافه شود
1. **ذخیره فایل JSON:** همیشه از `_wj()` استفاده کنید (atomic write)
1. **هیچ await در `spam_check` نباشد:** باید sync بماند
1. **`query.answer()` فقط یک بار:** هر callback فقط یک‌بار answer می‌زند
1. **`INSERT` همیشه با نام ستون:** `INSERT INTO users VALUES(...)` بدون نام ستون،
   با افزودن هر ستون جدید می‌شکند
1. **حذف یک بخش:** کلید آن را از `DEFAULT_MENU` بردارید — `load_menu()` خودش
   دکمه‌ی منسوخ را از `menu.json` کاربران پاک می‌کند
1. **`/start` باید همیشه `main_menu()` بفرستد:** تلگرام هر پیام را فقط با یک نوع
   کیبورد می‌پذیرد، پس دکمه‌های inline نباید جای منوی پایین را بگیرند
1. **هیچ‌وقت `users.db` را زیر پای اتصالِ باز جایگزین نکنید** — بخش ۱۱ را ببینید
1. **از `ctx.bot` استفاده کنید، نه `query.message._bot`** (API خصوصی PTB)
1. **`Forbidden` را همیشه بگیرید:** یعنی کاربر ربات را بلاک کرده →
   `mark_left(uid)` بزنید
1. **لینک دکمه‌ها را با `normalize_url()` اعتبارسنجی کنید:** لینک نامعتبر
   باعث می‌شود تلگرام کل پیامِ آن بخش را رد کند و بخش برای همه از کار بیفتد
1. **شناسه دکمه با `new_btn_id()`:** `int(time.time())` ثانیه‌ای بود و دو دکمه
   در یک ثانیه شناسه یکسان می‌گرفتند (حذف، هر دو را پاک می‌کرد)
1. **`_rj` فایل خراب را به `.corrupt` منتقل می‌کند** — دست نزنید، وگرنه
   ذخیره‌ی بعدی محتوای فروشگاه را با پیش‌فرض بازنویسی می‌کند
1. **`post_shutdown` باید حتماً `db.close()` بزند:** `aiosqlite` یک رشته‌ی
   non-daemon می‌سازد؛ اگر اتصال باز بماند پروسه هرگز خارج نمی‌شود، سرویس در
   حالت `deactivating` گیر می‌کند و نسخه‌ی جدید با قدیمی روی `getUpdates`
   تداخل (`Conflict`) پیدا می‌کند — ربات عملاً می‌میرد
